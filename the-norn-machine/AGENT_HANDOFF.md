## Scoring v4 Default: Bayesian Choice Model and X-Ray v2 (2026-10-20, uncommitted)

New profiles are `norn.profile.v4` / `norn.scoring.v4` (preview `norn.preview.v4`). The learned model is `norn.choice.seq-mnl.v1` in `backend/choice_model.py`, standard library only. Profiles v1–v3 keep their own code paths and replay unchanged; the 979-feature ranker (`preference_model.py`, `norn learn` / `norn rank`) stays available but is no longer the default. Read `docs/learning.md` ("Scoring v4") first.

- Why: the 2026-10-20 review found the 979 dimensions were 64 pixel statistics + 76 trait one-hots that are a 1:1 function of the card's type + 839 motif one-hots, 630 of them on a single card (card-ID memorisation). Its planted-preference simulation (now `scripts/model_comparison_planted.py`, `benchmarks/results/model-comparison-planted-v1.json`) is weak evidence for v4. Axis users are planted on the 4-D model's own coordinates, so 0.92 vs 0.74 is built in. The 12-D hybrid loses to 979-D on pixel (0.73 vs 0.75) and motif (0.56 vs 0.61) users. The model families also differ in objective and stop modelling, not only dimension. See docs/learning.md; real held-out choices decide (`norn records evaluate`).
- Features (12): the four hand-authored type coordinates / 8 (every card is ±1 per axis) and 0.5 × the first eight principal components of the 64 pixel statistics (unit sd; together ~70% of their variance). `backend/config/choice_features.json` is generated by `scripts/prepare_choice_features.py` (NumPy at generation only; `--check` verifies it is current) and cross-checked against `cards_metadata.json` at load.
- Labels: per completed round, the cards still selected at close, in first-click order, are sequential choices among the remaining displayed cards plus a "stop" option, ending with stop. A no-pick round is one stop choice; an all-pick round's final forced stop carries no information. In `norn.events.v2`, cards outside `round_completed.seen_card_ids` leave the choice set (same rule as the 979-D ranker; `null` keeps all). Withdrawn cards are not negatives.
- Fit: prior w ~ N(0, I/1.5), stop bias ~ N(0, 1/0.5); Newton to |step| < 1e-9; Laplace covariance. Outputs: posterior mean/sd/covariance of the 4 axis weights, stop bias, utilities for all 256 cards, top-6 cards, up to 4 most probable axis sign patterns ("types") from 4,096 fixed quasi-random draws (Halton 2/3/5/7 + antithetic), a chronological-holdout choice log-loss versus a uniform baseline and a stop-only baseline fitted on the same training rounds (`beats_baselines` = beats both, and is what the v5 prompt's `evidence_clarity` and the mock reading use; ≥5 completed rounds, ≥3 held-out choices), and a verifiable per-feature contribution block (`analysis.preference.contributions`, `choice_model.verify_contributions`, a rounded per-round copy in the trajectory for the X-Ray 工程细节 table; never in the language context). ## Cloudflare Adapter

Read `docs/deployment.md` and `cloudflare/src/entry.py`. Static Assets serves the included frontend and 256 cards; a thin Python gateway forwards API request streams by RPC to a browser-isolated SQLite `NornSession` Durable Object. The actor calls the same `NornService`, replay, and learning modules as local Python. No second JavaScript scorer is allowed.

Health initializes the opaque `__Host-norn-actor` cookie before interactive requests. It is HttpOnly/Secure/SameSite=Strict, not an identity login. Every API response renews its Max-Age=1800 routing lifetime without changing any session/receipt's absolute expiry. Each actor keeps one current reading and at most 40 paid-operation receipts. `norn/actor_state.py` restores strict detached JSON with absolute epoch expiries, frozen history, and settled results/errors, never locks or active operations. Actor v1 remains a mock session; actor v2 freezes the validated nonsecret generation route and attempt counter. The provider key is never persisted. `norn/cloud_provider.py` is the only hosted live transport: official `https://api.deepseek.com/v1/chat/completions`, model `deepseek-flash`, `thinking: {type: disabled}`. Keep the API key only in transport scope, not actor state/config snapshots, receipts, frontend, exports, logs, raw provider data, or prompts. Persist only sanitized numeric usage and bounded IDs. Errors remain explicit; no automatic retry, provider fallback, or silent mock prose.

`norn/cloud_host.py` orchestrates the shared prepare/finish stages around awaited HTTP. Commit a pending SQLite receipt before any paid HTTP. Reserve the global quota, then durably increment the browser attempt counter before dispatch. Settle the response receipt and conversation snapshot in one synchronous transaction on the actor's SQLite store. On uncertain pending outcomes, the same ID returns 409 and must never resend; only explicit new-ID retry creates another attempt. Same-ID different content is 409. A quota-admission 429 occurs before dispatch, discards its pending reservation, and permits retry with the same ID. Terminal upstream failures remain settled, consume attempts, and do not consume a successful dialogue turn.

`NornBudget` is a separate short SQL coordination atom, not a centralized conversation actor: global 100 admitted attempts/UTC day, four concurrent calls, 120-second leases. Each browser actor also has 12 attempts, persistent across restarts/new readings until all of its 30-minute session/receipt records expire and state is cleared. ## 3. Runtime and Session Contract

Local flow:

1. The browser loads all static resources from the Python server.
2. The browser sends `{"journal": ...}`. The analysis API validates every event and transition, then derives the scoring projection; a legacy snapshot remains an explicitly labeled compatibility route.
3. The service builds profile v4 by fitting the current journal's Bayesian choice model under the portable numerical contract and freezing its posterior summary/feature version (profile v3 instead froze the 979-feature checkpoint). v4 computes no `fast_thinker.py` coordinate projection; its `analysis.attribution` holds only source-event evidence. In v1–v3 profiles that projection and its ledger remain historical reference with exact reconstructible accounting.
4. The selected provider returns prose and generation metadata.
5. A successful analysis creates an opaque server session. Follow-ups use its stored profile and successful history; client-supplied profile, history, or turn counts are not authoritative.

Local-server sessions live **only in process memory**, expire **30 minutes after creation**, and are capped at **256** entries. Capacity may evict an older session. Restart loses those local sessions. There is no local database, cross-user memory, or durable profile persistence. Do not describe the local runtime as stateless. The Cloudflare adapter's bounded SQLite actor persistence is separate and described above. Session expiry requires a new reading.

Dialogue allows one, two, or three turns according to the existing round-based rules and caps input at 100 characters. A failed provider response does not consume a successful dialogue turn. Analysis and dialogue now share the same common rules, frozen profile/evidence prefix and native role history; each turn adds only its user input and current-turn instruction. Server history begins with `build_analysis_prompt(context)['messages']` followed by the successful assistant reading. After a successful follow-up, retain the returned full prompt messages and append the assistant reply. Do not reconstruct old user messages or strip the initial request; the builder verifies the authoritative prefix and turn length.

This release includes complete event replay, versioned profiles, a full historical coordinate ledger, learned ranking contributions, frozen native-history contexts, X-Ray inspection (v2: per-round choice-model trajectory; the what-if replay UI was removed), and portable packaging. The model context contains bounded learned-preference summaries and at most eight selection/four revision evidence rows with event IDs; full events/accounting stay outside the bounded prompt. The context is `norn.context.v1` and current production prompt is `norn.prompt.v4`. Revision evidence explicitly carries final_selected and, when selected, final_selection_event_id. Samples must not be treated as totals or used to assert what omitted events did. Dialogue templates are loaded once per process so source edits cannot silently alter an active process's contract. Prompt/cache dispatch metadata and provider observations must remain distinct. Offline tests and repeated prefixes do not establish a real cache saving.

### Event, Profile, and Replay Contract

- Journal envelope: `{"schema_version":"norn.events.v4","events":[...]}` (the browser writes v4 after the 2026-10-21 compatibility review; `norn.events.v1`, `v2` and `v3` remain accepted and replay unchanged). Each event has a unique 1–64 character printable ASCII `event_id` without spaces, a continuous integer `sequence` from 1, and an explicit `type`. Exact fields and JSON types are enforced. Unknown fields/schema/types/cards, coercions, nonfinite values, sequence gaps, and impossible transitions fail before rendering.
- `round_started` has `round` and `card_ids` (1–256 unique known cards), beginning at round 1 and continuing consecutively only after closing the previous round. `card_selected` / `card_deselected` have `round` and `card_id`, and require the open round's display evidence. Selecting an active card or canceling an inactive card fails. Earlier selections can be canceled if displayed again in a later round. Reselecting creates a new active-order position and source ID.
- `round_completed` closes the open round and has integer `duration_ms` from 0 to 86,400,000. `session_completed` has no extra fields, requires at least one completed round with none open, and seals the journal against any suffix. Limits: 256 rounds, 256 active selections, 10,000 total events including closure. There is no separate revision cap on journals. Legacy snapshots retain their 4,096-revision compatibility limit.
- v2 only: `round_ready` {`round`, `ready_offset_ms`, `unloaded_card_ids`} once per round when every image loaded, failed or timed out (8 s), and before any choice; choices add `t_ms` (ms since `round_ready`, non-decreasing); `round_completed` adds `hidden_ms` (tab hidden after readiness, at most the measured window) and `seen_card_ids` (≥50% visible with the image shown, first-seen order; `null` when the browser cannot observe). A round may close without `round_ready` (skipped while loading). Preference labels use displayed ∩ seen when visibility is known.
- v3 adds raw behaviour that no model reads yet; it is collected so a later model can be tested against held-out choices.
  - `round_ready.layout`: the `[row, column]` screen slot of each displayed card in `card_ids` order. It is read from layout offsets, not animated boxes, and is `null` when not measurable or when two cards would share a slot.
  - `card_selected` / `card_deselected` `.input`: `mouse` / `touch` / `pen` / `keyboard` / `null`, taken from the press that led to the click.
  - `round_completed.hover`: mouse/pen hover segments `[card index, start_ms, end_ms]` from readiness, ordered, non-overlapping, inside the measured window and capped at 512. It is `null` where the device cannot hover and on rounds that never became ready. A hidden tab ends the open segment, and touch never counts as hover.
  - Scoring inputs, choice posteriors and 979-D model weights are identical for a v3 journal and its v2 projection (`tests/test_event_replay.py`). Full `events_hash` and `profile_hash` differ because the raw journal is part of their identity. The browser's own output is replayed through the Python validator (`tests/test_frontend_events.py`).
- v4 adds `.layout` to every `card_selected` / `card_deselected`, using the same coarse `[row, column]` format in displayed-card order. It captures the actual choice-time layout after resize, orientation or drawer changes. `round_ready.layout` remains the initial layout. Replay exposes choice snapshots separately as `round_evidence.choice_layouts`; they do not enter fitting. Hover resumes after returning to a visible tab only when the card still matches `:hover`; hidden time and an unconfirmed old pointer position do not count. Historical v3 event/profile hashes are pinned in tests and unchanged.
- Optional outcome label: `POST /api/feedback` {`session_id`, `reading_rating` 1–5|null, `closest_card_id`|null} stores a `norn.post_session.v1` record on the session (never in the journal; `validate_post_session()`); exports add it as an optional top-level `post_session` key, which `replay_bundle()` validates but never hashes.
- `replay_events()` returns detached `journal`, scoring `input`, matching `selection_event_ids` / `revision_event_ids`, `round_evidence` (v2 timing/visibility, v3 initial `layout` and `hover`, v4 `choice_layouts`; `None` for v1), `events_hash`, and `complete`. By default it requires a sealed session. `append_event()` validates a full new event into a new journal copy; it never changes the previous copy. These helpers have no disk store, database, model call, or transaction engine.
- Default profile versions: `schema_version: norn.profile.v4`, `algorithm_version: norn.scoring.v4`, with choice model `norn.choice.seq-mnl.v1`, `feature_version`, and `numerical_contract: norn.numeric.decimal34.v1`. Profile/scoring v3 (979-feature ranker, same contract) remains supported; legacy profile/scoring v1 and v2 remain supported under their original native-libm semantics. v4's `analysis.attribution` is the evidence-only `norn.attribution.v3`; v3 profiles nest the historical ledger `norn.attribution.v2`, which is not the learned score ledger. Old attribution v1 is unchanged for historical profiles. `metadata_version` hashes loaded legacy card metadata, while learned feature identity is separately hashed. Compact finite UTF-8 JSON with sorted object keys defines SHA-256 encoding. `events_hash` covers the entire journal; `profile_hash` covers all profile fields except itself. Generated prose, provider usage, clocks, random session IDs, and credentials are excluded.
- Bump the scoring version when rules or their numeric semantics change, and bump the affected schema when its meaning or structure changes. Never reuse a supported version to silently reinterpret saved records.
- Event profiles have `source: event_journal`. Legacy profiles have `source: legacy_snapshot`, validated `input` and `snapshot_hash`, and no `events_hash`. Legacy bundle `journal` is null; stable synthetic ledger IDs identify entries, not recovered clicks. Never fabricate a click sequence from a snapshot or describe legacy replay as complete interaction replay.
- `fast_think()` is the authority for the historical coordinate projection and returns analysis plus `attribution`; it accepts source event IDs as optional keyword arguments. `preference_model.py` is the learned ranking authority. The coordinate ledger records duration clamp/normalization, base weights, hesitation multipliers, weighted coordinates, normalized weights, base contributions, hesitation effects, final contributions, and revision allocations. `weight_summation_delta` / `base_weight_summation_delta` preserve sequential weight accumulation residuals.
- Each final coordinate reconstructs with `math.fsum(selection contributions + revision deltas + summation_delta + rounding_delta)`. `summation_delta` preserves the original sequential floating-point accumulator; `rounding_delta` preserves final two-decimal rounding. `ledger.reconstruct_coords()` sums entries rather than trusting stored final values; `verify_attribution()` checks all dimensions and accounting with 1e-12 absolute tolerance. The J/P correction is a single capped session adjustment using the existing two-decimal strength. Its event shares are bookkeeping, not psychological causality; the last share absorbs float remainder. Empty selections retain zero coordinates and mark revisions unapplied.
- `export_replay(journal)` creates `{"schema_version":"norn.replay.v1","journal":...,"profile":...}`. `build_replay_bundle(profile,journal=None)` supports event and legacy sources. `verify_profile()` / `replay_bundle()` verify hashes, supported versions and metadata, then recompute and compare the entire analysis/ledger. Changed metadata, unsupported versions, or altered derived fields fail; there is no automatic migration. Hashes establish content consistency, not authorship or proof of real browser behavior.
- Endpoints: `POST /api/analyze` takes `{"journal":...}` without mixed snapshot fields; `GET /api/sessions/<session_id>/export` downloads the live session's frozen bundle; `POST /api/replay` takes a raw complete journal or bundle directly and returns a verified profile and reconstructed coordinates without calling a model or creating a session. Full events and ledger are not included in model prompts.
- Exports include only the initial journal (or null for legacy), frozen profile, and ledger. They omit reading/follow-up text and provider usage. Successful/failed follow-ups cannot change the profile hash or export. Local restart or session expiry removes access to the server copy; Cloudflare actor eviction alone does not.
